## What Was Built In T0129

T0129 trained a portable learned post-Hybrid hard-negative veto for the sibling STIGA app's guarded `Hybrid 2.0` mode.

The idea was:

```text
existing STIGA Hybrid accepts a candidate
-> learned veto decides hard_positive vs hard_negative
-> keep only likely hard_positive candidates
```

The model is not a full bounce detector. It only runs after existing Hybrid says yes.

## Training Source

Training source CSV:

```text
data/audio/models/evaluations/t0104e_live_positive_candidate_loop/t0104e_candidate_rows.csv
```

Training script:

```text
skills/pingis-audio-classification/scripts/noise_robust/train_t0129_hybrid_hard_negative_veto.py
```

The script replays the same STIGA Hybrid app models:

```text
apps/collector/src/models/audio_contact_model.json
apps/collector/src/models/audio_model.json
```

It keeps only rows that plain STIGA Hybrid would accept:

- contact model label must be `racket_contact`
- contact confidence must be at least `0.25`
- 4-class surface model must not strongly veto as `table_bounce`, `floor_bounce`, or `noise`
- surface veto confidence is `0.75`
- app-style merge is `180 ms`

Accepted true bounces become `hard_positive`.
Accepted false positives become `hard_negative`.

## Critical Live Result After Porting To STIGA

After porting the exported JSON into `stiga-app-v2` as `Hybrid 2.0`, Love tested 10 clear bounces.

Live WebView inspection showed:

```text
10 Hybrid candidates appeared in the log
1 row was COUNT #1
9 rows were DROP learned-veto
```

Example rows:

```text
p=78%, veto=32%, learned-veto
p=81%, veto=35%, learned-veto
p=80%, veto=17%, learned-veto
p=77%, veto=42%, learned-veto
p=75%, veto=65%, COUNT #1
```

Interpretation:

- `p` is original Hybrid/contact confidence.
- `veto` is the learned hard-positive probability.
- Final Hybrid 2.0 currently uses `veto >= 0.45`.
- The learned veto is too strict or not portable enough for the live phone/setup.

Do not treat T0129 as promotion-ready despite the offline OOF result.
